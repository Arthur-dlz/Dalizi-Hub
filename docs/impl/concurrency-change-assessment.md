## 2. 问题分解：这是两个不同的问题

- **P-调度层**：dispatcher 单任务语义（busy 拒单）→「第二单怎么办」。改的是 dispatcher + 蓝图。
- **P-工作区层**：两个 CLI 进程**同时**在同一项目目录里读写 → 文件互踩（未提交改动、构建产物、`node_modules`、测试现场）。agy/codex 的权限白名单按**目录**不按 job 授权，两个 job 同目录无隔离。**这才是同项目并行的真正风险墙**，且它不在 dispatcher 控制面内。

**关键判断：只改调度层不改工作区层 = 把冲突从「拒单」变成「互踩」，风险反而更大。**

## 3. 选项矩阵

| 选项 | 语义 | 改动面 | 蓝图修订点 | 风险 | 量级 |
|---|---|---|---|---|---|
| **A. 实例内 FIFO 队列** | 第二单不拒，排队等前单终态后自动启动；同一时刻仍只跑一个 | dispatcher：activeJobId→pending 队列（准入区间内入队、终态后按序取）；快照 QUEUED 长存展示；恢复扫描对排队项的分类；卡片排队位置展示 | §4:94 准入语义；§5:103「不代表排队产品」句重写；§7:162 恢复扫描决策表（QUEUED 长存项）；§11:230 范围外句 | 低-中。**工作区天然安全（仍串行执行）**；衍生问题=排队可见性与「不想排了」诉求（取消仍是非目标，须定义排队项移除路径） | 中卡（1 张施工卡+测试） |
| **B. 实例内有界并行（N>1）** | 同实例同时跑 N 个 job | admission 改计数信号量；JobStore 已 per-job 串行（兼容）；心跳/恢复按 owner/child 对（兼容） | §4/§5/§7 多处；§11 | **高：P-工作区层无解**——两个 CLI 同目录同时写，互踩不可控 | 大改+不可控风险，**不推荐** |
| **C. 维持单任务 + busy 体验优化** | 拒单不变，但 agent 协议约定（拒单后告知并稍后重试）；零代码协议已固化（OPERATIONS §3.3.1） | 已在跑，零蓝图变更 | 无 | 低 | 已落地 |
| **D. 同项目多实例**（独立状态目录+独立端口） | 两个 dispatcher 实例指向同一项目目录 | 部署面（bridge 多实例托管、端口规划、客户端多连接） | §11 拓扑段（原意图是多项目） | **高：同 B**——实例互不知晓，工作区互踩；幂等命名空间还分裂（§4:91 跨实例不查重，同 request_id 会双跑） | 不推荐 |
| **E. git worktree per job** | 每 job 一个 worktree，物理隔离工作区后真并行 | worktree 生命周期管理+CLI 环境复制（node_modules/状态文件不入 worktree）+合并路径 | 全新章节 | 中-高；且用户已评估过 worktree **决定不开**（2026-10-01，集成成本高、隔离收益不足） | 与既往决策冲突，不列正式选项 |

## 4. 评估结论（主控建议）

1. **B/D/E 全部撞 P-工作区层这堵墙**：「真并行」在同项目目录内没有安全落地方案（除非上 worktree，已被否决）。**同项目真并行 = 不建议做，不是不能做，是做了会把故障模式从显式拒单变成隐式互踩。**
2. **A（FIFO 队列）是唯一值得立项的变更**：它不动工作区安全模型（串行执行不变），只把「第二单直拒」变成「第二单被收下等待」——**解决的恰是用户体感痛点（"第二单石沉大海"），而不是执行速度**。
3. **先确认真需求**：用户痛的是「拒单体验」还是「执行吞吐」？前者=A 足够；后者=只有多项目拆分（已支持）或 worktree（已否决）。**从操作习惯证据（多窗口并行派单）看，痛的更可能是前者。**
4. 过渡期内 C 已在跑（OPERATIONS §3.3.1 协议：busy 非丢单、重试安全）。

## 5. 若立项 A：最小变更范围（供拍板后出卡）

- **蓝图**：§4:94 准入语义（入队纳入串行区间）；§5:103（状态机 QUEUED 长存合法化 + 排队产品边界声明：FIFO、无优先级、**无取消**（排队项仅可在未启动前经人工命令移除，复用 resolve-recovery 式人工路径，不开取消工具））；§7:162（恢复扫描：未启动的排队项=确认未启动可失败收尾 or 保留排队？须拍板）；§11:230（范围外句移除）。
- **代码**：`dispatcher.js` 准入链（activeJobId→`#pendingQueue`；终态回调里按序启动）；`job-store`（QUEUED 长存快照已支持，无需改）；`mcp-server.js`（dispatch 回执增 `position` 字段）；`task-card.html`（QUEUED 展示「排队中（第 N 位）」）。
- **测试**：排队 FIFO 顺序、busy 变入队、终态自动启动、恢复扫描对排队项分类、幂等命中排队中 job、回执 position。
- **不碰**：实例锁、幂等命名空间、工作区模型、runner 三件套。
